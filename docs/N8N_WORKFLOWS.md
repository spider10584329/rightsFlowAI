# n8n Workflows

Exports live in `automation/n8n/workflows/`. Six files are generated by `automation/n8n/build_workflows.py`:
- `royalty-import.json`
- `contract-expiration.json`
- `ai-metadata-review.json`
- `monthly-reporting.json`
- `automation-health.json`
- `automation-error-handler.json`

They were built and tested against **n8n 2.43.5** with these node versions:
- Manual Trigger 1
- Schedule Trigger 1.2
- Code 2
- HTTP Request 4.2
- If 2.2
- Read/Write Files from Disk 1
- Error Trigger 1
- No Operation 1

Every workflow follows the same rules:
- The **Config** Code node holds non-secret settings. `__RIGHTSFLOW_API_URL__`,
  `__RIGHTSFLOW_INBOX__`, `__RIGHTSFLOW_N8N_URL__` and `__RIGHTSFLOW_INSTANCE_ID__` are filled in
  when you import with `scripts/setup-n8n-automation.ps1`.
- API calls use the **"RightsFlow automation key"** credential (Header Auth, id
  `RfAutomationKey1`). The exports hold only that reference, never the key.
- **Start run** (`POST /automation/runs`) and **Finish run** record the execution:
  - the n8n execution id
  - the trigger (manual or schedule)
  - a summary (counts only)
  - the status: `succeeded`, `partial`, `failed` or `skipped`
- Every authenticated call sends `X-Automation-Instance: <instance id>`. The API binds a key to
  the first instance that uses it and refuses others with 409 `instance_conflict`.
- Every POST sends `Idempotency-Key: <instance id>:<step>-<execution id>[-<item>]` (namespaced
  per instance, so a reset n8n database restarting its execution ids can't collide) and
  `X-Correlation-ID: n8n-<execution id>`.
- HTTP nodes retry 3 times, 5 seconds apart. The report "Notify recipients" step retries 5 times,
  10 seconds apart. These node retries are **fixed-interval** (n8n has no backoff option); they
  only bridge short blips. Longer outages are handled by the API: outbox leases with exponential
  backoff for events, and the statement retry state (below). Accepted limitation (audit N8N-11).
- Steps whose outcome is data (duplicates, rejected files, reminders that aren't due) use
  `neverError`, so the outcome reaches the summary instead of failing the run.
- Workflow setting **Error workflow** points at `RightsFlow - Automation error handler`.
- Execution order is `v1`, and the timezone is UTC.
- The API decides everything that matters: duplicates, due dates, authorization, money. The
  workflows only route data.

## A. Royalty statement import (`RfWfRoyaltyImprt`)

**Triggers:** Run now (manual) or every 15 minutes.

```
Config → Start run → Read inbox files ─┬─(files)─→ Describe file → Upload statement ─┐
                                       └─(none)─────────────────────────────────────┴→ Claim statement events
→ Collect statements → Anything to process? ─(yes)→ Start processing → Wait for processing
                                             │       → Review results → Summarize → Finish run
                                             └─(no)───────────────────────────────→ Finish run
```

**Inbox upload**
1. *Read inbox files* reads `<inbox>/*.*`. File access is restricted to that folder.
2. *Describe file* parses the name `<category>__<source>__<YYYY-MM>[__<CUR>]`. Invalid names are
   sent with an invalid category, so the API rejects them with 422 and the summary lists them.
3. *Upload statement* sends `POST /automation/statements` (multipart). The API applies the app's
   checks: type and size, archive-bomb protection, parsing, and duplicate detection by file and by
   content. **Formats:** CSV and XLSX (verified with real local fixtures: XLSX amounts stay exact,
   formulas are not executed). Legacy `.xls` and anything else are rejected with
   `unsupported_file_type`.
   - Every file gets a stored outcome keyed by its SHA-256: `imported`, `duplicate` or `rejected`
     (with the reason). A file that was already imported comes back as `200 {duplicate: true}`.
   - A rejected file raises **one** `inbox_file_rejected` review task and notification; later runs
     report it as `seen_before: true` without new tasks.
   - Files stay in the inbox (n8n's file access is restricted to it); remove them when done.

**App uploads**
4. *Claim statement events* leases `statement.uploaded` and `statement.ready` events. An app
   upload is **not processed until a person confirms its column mapping** in the app; confirming
   emits `statement.ready`. Until then the statement is reported as `awaiting_mapping` and the
   event is acknowledged. Automation never confirms mappings or invents default mappings.

**Processing and review**
5. *Start processing* (`POST /statements/{id}/process`) is idempotent and drives a durable
   per-statement state (`automation_statement_states`):
   - `processing` → `completed`;
   - a **transient** failure (lost connection, timeout, deadlock) → `retry_waiting` with
     exponential backoff (15 min × 2^(attempt−1)), at most 3 attempts;
   - a **permanent** failure (invalid data) or exhausted retries → `needs_manual_review`, managers
     notified once; a manager restarts it with **Retry** (Settings → Automation → Statements);
   - an inbox statement whose mapping is unusable → `awaiting_mapping` with a mapping task.
   Failed statements are never reprocessed on every run. The state survives restarts of n8n and
   the API.
6. *Wait for processing* (`GET /statements/{id}?wait_seconds=45`) is a bounded long-poll.
7. *Review results* (`POST /statements/{id}/review`, with `calculate: true`):
   - The API calculates a **draft** run so that held money is visible.
   - It returns counts: unmatched lines, invalid lines, and lines **held** by reason (missing or
     ambiguous contract terms, disputed or missing ownership…).
   - It creates or updates one review task per statement and notifies managers once per distinct
     set of findings.
   - For event items, it acknowledges the outbox event in the same request.
   - **Nothing is posted.** Posting stays a human admin action in the app.

**Not automated:** posting runs, matching unmatched lines, confirming column mappings and
approving disputed royalties. These show up as review tasks.

## B. Contract expiration reminders (`RfWfContractExpr`)

**Triggers:** Run now or daily at 07:00 UTC. Thresholds are set in Config: `[30, 14, 7]` days.

```
Config → Start run → List expiring contracts → Plan reminders → Any reminders due? ─(yes)→ Send reminder → Summarize → Finish run
                                                                                  └─(no)──────────────────────────→ Finish run
```

1. *List expiring contracts*: `GET /contracts/expiring?within_days=30`. It returns ids, dates and
   status only. Active and pending contracts are included, as well as contracts already past
   their end date.
2. *Plan reminders* picks the tightest threshold reached, or `0` for already expired.
3. *Send reminder*: `POST /contracts/{id}/reminders {threshold_days}`.
   - The API re-checks that the reminder is due (422 `reminder_not_due` otherwise).
   - It notifies managers and above, with email following their preferences.
   - It records one delivery per contract, end date and threshold. Repeats come back with
     `duplicate: true`, so there are no duplicate reminders.
   - If no member can receive it, the delivery is recorded as `skipped` with reason `no_recipients`.

The app's built-in daily job still sends its own single warning at the organization's warning
window (60 days by default). The workflow adds the 30/14/7-day and "expired" reminders.

## C. AI metadata and rights review (`RfWfAiReview0001`)

**Triggers:** Run now or every 30 minutes.

```
Config → Start run → Claim review events → Collect subjects → Anything to review? ─(yes)→ AI review → Record human decisions → Summarize → Finish run
                                                                                  └─(no)──────────────→ Record human decisions
```

1. *Claim review events* leases these event types:
   - `work.created`
   - `recording.created`
   - `review.requested` (a person clicked **Request automated review**)
   - `rights_conflict.opened` (high or critical severity)
2. *AI review* calls `POST /automation/ai/review`. It sends one item at a time, 500 ms apart.
   - **Works, recordings and parties:** the app's AI metadata cleanup. Output is checked against
     the structured schema and per-field rules, then stored as **pending** suggestions. The step
     also records the deterministic validation issues.
   - **Rights conflicts:** an AI explanation stored as an **advisory** review note. The conflict
     itself is never changed.
   - The step acknowledges the event.
   - Outcomes:
     - `suggested`
     - `explained`
     - `no_changes`
     - `ai_unavailable` (no provider, or the plan has no AI)
     - `ai_limit_reached`
     - `ai_error` (timeout, rate limit or invalid output)
3. *Record human decisions* (`POST /ai/sync-decisions`): after a person approves or rejects every
   suggestion in the app, the review task is closed with that decision.

**Human decision:** approving a suggestion applies it through the existing validated catalog
service, and only if the field hasn't changed since the suggestion was made. The workflow never
applies anything itself.

## D. Monthly royalty report (`RfWfMonthlyRprt1`)

**Triggers:** Run now or monthly on the 2nd at 06:00 UTC. Config sets the report type
(`revenue_by_source` by default) and the period (the previous calendar month).

```
Config → Start run (key monthly:<type>:<YYYY-MM>) → Already delivered? ─(yes)→ Nothing to do
                                                                       └─(no)→ Request report → Wait for report → Notify recipients → Summarize → Finish run
```

1. *Start run* uses a business idempotency key. If that month's run already succeeded, the
   workflow stops.
2. *Request report*: `POST /reports/monthly`.
   - It queues the app's existing report job. The figures come from RightsFlow data, and n8n
     never sees or computes them.
   - It records one delivery per report type and month.
   - Only **completed** months are accepted.
3. *Wait for report*: `GET /jobs/{id}?wait_seconds=50`.
4. *Notify recipients*: `POST /reports/deliveries/{id}/send`. Only active **admins and owners**
   are notified; a named recipient must be one of them. The message is a link into the app with
   no figures. A repeat returns `duplicate`.

## E. Automation health check (`RfWfHealthCheck1`)

**Triggers:** Run now or hourly.

```
Config → Check n8n → Check API → Check automation API → Diagnose → API reachable? ─(yes)→ Start run → Finish run → Problems found? ─(yes)→ Alert admins
                                                                                   └─(no)─→ Fail loudly
```

The checks use `neverError` and `continue on error`, so an unreachable service is *reported*,
not a crash.

*Diagnose* uses the API's own `issues` list (`GET /automation/health`) and produces a report in
this format (values illustrative):

```
HEALTHY  n8n: HTTP 200
HEALTHY  FastAPI: HTTP 200
WARNING  Automation key: expires in 10 day(s)
HEALTHY  Database, outbox, runs, incidents: database 1.2 ms
```

- `overall` is `healthy`, `warning` or `critical`.
- **Key expiry:** `warning` at 14 days or less, `critical` at 3 days or less (settings
  `AUTOMATION_CREDENTIAL_WARNING_DAYS` / `_CRITICAL_DAYS`).
- **Other issues from the API:** dead events, runs stuck for more than 6 hours, failed runs with
  no later successful run, and open incidents of other workflows.
- When there are problems, *Alert admins* raises an incident. It is deduplicated like every other
  failure, so an hourly warning alerts once, then reminds once per suppression window.
- **Fail loudly:** if the API can't be reached, or rejects the key (401/403) or the instance
  (409), nothing can be recorded there. The execution then fails visibly, in n8n's Executions list
  and through the error workflow.
- The backend's daily maintenance job also notifies admins about expiring keys, independently of
  n8n. `scripts\check-n8n.ps1` gives the same diagnosis locally.

This checks availability and readiness only; it doesn't prove that business workflows produce
correct results.

## Error handler (`RfWfErrorHandler`)

**Trigger:** Error Trigger. It runs when any workflow above fails. n8n only runs **published**
error workflows; `setup-n8n-automation.ps1` publishes it, and it has no schedule.

It calls `POST /automation/alerts` with the workflow name, the execution id, the last node
(`resource`) and the error message. The API:
- redacts secrets;
- marks the matching run failed (found by execution id);
- logs every failure in the audit log (`automation.workflow_failed`);
- groups failures into **incidents** by workflow, error category (authentication, connection,
  timeout, rate_limited, server_error, client_error, health, workflow_error) and node, per
  organization;
- alerts admins once per new incident, suppresses repeats for 60 minutes and then sends one
  reminder per window, and notifies owners once at 10 occurrences (escalation);
- resolves the incident, with one "Recovered:" notice, when a later execution of the workflow
  succeeds.

Verified inside the running n8n server: a scheduled workflow that fails every minute produced
error-mode executions of this handler, and one incident with one alert (repeats suppressed).

## Changing the workflows

1. Edit `automation/n8n/build_workflows.py`, then run
   `backend\.venv\Scripts\python.exe automation\n8n\build_workflows.py`.
2. Re-import with `scripts\setup-n8n-automation.ps1`.

If you edit in the n8n editor instead, export with `Invoke-N8nCli export:workflow` and port the
change back to the generator. Otherwise the next import overwrites it, because imports reuse the
same workflow ids.
