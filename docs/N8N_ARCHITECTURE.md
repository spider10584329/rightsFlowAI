# n8n Automation Architecture

```
Browser ──► Next.js (BFF, :3000) ──► FastAPI (:8000) ──► MariaDB (XAMPP, :3306)
                                         ▲    │
                      automation API key │    │ transactional outbox (automation_events)
                                         │    ▼
                                     n8n (:5678, 127.0.0.1 only; own SQLite DB)
```

n8n **orchestrates**: schedules, event polling, retries, notifications and run tracking.
FastAPI **decides**: authentication, authorization, tenant isolation, catalog, rights, contracts,
royalty calculation, ledger, payouts and audit. n8n never connects to MariaDB and never computes
money. Every n8n action is a call to `/api/v1/automation/...`, which reuses the existing services.

## Authentication model

- An admin creates an **automation credential** for one organization. The token
  `rfa_<key_id>_<secret>` is shown once. Only `HMAC-SHA256(pepper, key_id:secret)` is stored.
- Each credential has its own **service user** (`users.is_service_account = 1`). That user:
  - can't sign in, refresh tokens, use email links or receive notifications;
  - is **not** an organization member, so it uses no seat and is invisible in team lists;
  - is what audit logs and `created_by` columns show for automated changes.
- On each request the key is checked (constant-time) for revocation, expiry, an active
  organization and an active service user, and then for the endpoint's **scope**. The caller
  acts with a *transient* manager-level membership that is never stored. Existing services can
  be reused, but anything that needs admin rights (posting runs, approving payouts) stays out of
  reach. No automation route exists for those operations at all.
- Keys **rotate** with a grace period (the old key keeps working for 0–168 hours) and can be
  revoked at any time.

## Reliable event delivery (transactional outbox)

1. Business code calls `emit_event(...)` **inside its own transaction**: the event row commits or
   rolls back with the change. Events are emitted for:
   - `statement.uploaded` (a person uploaded a statement)
   - `work.created` and `recording.created`
   - `rights_conflict.opened` (high or critical severity)
   - `review.requested` (a person asked for a review)
2. n8n calls `POST /automation/events/claim`. A conditional `UPDATE` leases up to N due events
   with a random lease token, so two pollers can't claim the same event.
3. The workflow processes the event. The final call acknowledges it in the same request: the
   statement review and AI review endpoints accept `event_id` and `lease_token`. There is also
   `POST /events/{id}/ack` with `completed`, `retry` or `failed`.
4. If n8n crashes or stops, the lease expires and the next poll claims the event again. Every
   claim increments `attempts`, so a poison event becomes **dead** after `max_attempts` (5).
   `retry` acknowledgements back off exponentially (30 s × 2ⁿ, at most 1 h). Admins see dead
   events and can requeue them (`POST /organizations/{id}/automation/events/{id}/requeue`).
5. Completed events older than 30 days are purged by the daily `automation_maintenance` job.

## Idempotency and duplicate prevention

| Layer | Mechanism |
|---|---|
| HTTP | Every mutating automation call requires `Idempotency-Key` (8–128 characters). Replays with the same key and request return the stored response with `Idempotent-Replayed: true`. The same key with a different request returns 422. A concurrent duplicate returns 409. On error the key is released so the caller can retry. Keys are kept 7 days. |
| Workflow keys | n8n derives keys from `$execution.id` plus the business item, so n8n's own node retries are replay-safe. |
| Statements | The existing duplicate detection (same bytes, or same rows in a different format) always applies. The automation upload returns `200 {duplicate: true}` with the existing statement, so re-runs continue safely. |
| Notifications | Every reminder, review notice, report notice and alert goes through `automation_deliveries` with a unique dedupe key, for example `contract-reminder:<id>:<end date>:<threshold>` or `monthly-report:<type>:<YYYY-MM>`. |
| Runs | `POST /runs` with a business `idempotency_key` (for example `monthly:revenue_by_source:2026-09`) returns the already-succeeded run, so the workflow can stop. A failed run is restarted with `retry_count + 1`. |
| Review tasks | One task per subject (`statement-review:<id>`, `ai-metadata:<type>:<id>`…). Re-runs update the task only if the findings changed, and only notify then. |

## Observability

`automation_runs` stores one row per workflow execution:
- `workflow`, the n8n `execution_id`, `trigger_type` and `correlation_id` (`X-Correlation-ID: n8n-<execution id>`);
- the organization, the triggering `event_id`, `status` and `retry_count`;
- start and finish timestamps;
- a size-limited `summary` holding counts and ids only;
- a redacted `error_code` and `error_message`.

The error-handler workflow marks the run failed and alerts admins once per failed execution.
`GET /automation/health` and workflow E report the following:
- API and database status
- key expiry
- outbox backlog and dead events
- failed runs in the last 24 h, and runs stuck for more than 6 h

Admins see the same in `GET /organizations/{id}/automation/overview`, `/runs` and `/events`.

## Confidentiality in n8n execution logs

n8n stores execution data (14-day retention). Automation responses therefore carry statuses,
ids and counts, **not amounts, names of payees or document text**. For example, a statement
review returns line counts and hold *reasons*, never money. Report figures stay in the app:
n8n only learns that the report job succeeded, and recipients get a link.

## Workflow summary

| Workflow | Trigger (local test) | Steps (all through FastAPI) |
|---|---|---|
| A. Royalty import | Manual; every 15 min | Read inbox files (local intake) → upload (validation and duplicate checks) → claim `statement.uploaded` events → process → wait (bounded long-poll) → review (draft calculation, holds, review task, notify once, acknowledge event) → record run |
| B. Contract expiration | Manual; daily 07:00 UTC | List contracts expiring within 30 days → choose threshold 30/14/7/expired → reminder (server re-checks it is due; one per contract, end date and threshold) → record run |
| C. AI review | Manual; every 30 min | Claim catalog, review and conflict events → `/ai/review` (pending suggestions or advisory notes; acknowledge event) → record human decisions (`/ai/sync-decisions`) → record run |
| D. Monthly report | Manual; monthly on the 2nd, 06:00 UTC | Start run keyed by month (skip if already delivered) → queue the existing report job → wait → notify admins and owners once → record run |
| E. Health | Manual; hourly | Check n8n, API, database, key, outbox and runs → readable diagnosis → record run → alert admins once a day per problem set |
| Error handler | Any of the above fails | Mark run failed and alert admins |
